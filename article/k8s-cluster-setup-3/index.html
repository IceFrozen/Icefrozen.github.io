在集群节点或者内部 POD上访问我们的服务(修改 resolv.conf的方式)

在pod 内部访问服务，同时我们也可在集群的节点上来通过域名访问服务。因为我们的节点的 /etc/resolv.conf 默认指向 192.168.3.1（网关 DNS），解析不了 cluster.local。只需要把 CoreDNS 加为第一 DNS 即可（ClusterIP 在节点上可达，因为 kube-proxy 在每个节点都写了转发规则）：这里有个需要注意的一点就是，当我们使用两个 dns的时候，注意节点的 options 参数，
一般情况下我们会这么加：options ndots:5 timeout:1 attempts:2 single-request-reopen rotate
由于我们两个 dns 的解析是不同系统的，因此不可以增加 rotate 参数，否则会导致我们两个 dns 的解析是不同的，因此我们需要去掉 rotate 参数。

参数 含义 你当前场景的影响
ndots:5 域名中 . 少于 5 个时，优先尝试 search 域；达到 5 个则更倾向直接查询 Kubernetes DNS 常见配置
timeout:1 DNS 单次查询等待约 1 秒后超时 DNS 故障时失败得比较快
attempts:2 DNS 查询失败后的重试次数 最多进行多次尝试
single-request-reopen A/AAAA 查询遇到部分 DNS/NAT 兼容问题时重新打开 socket 一般可以保留，对 Kubernetes 没太大影响
rotate 多个 nameserver 之间轮换选择 你当前场景比较重要，可能导致一次走 CoreDNS，一次走 192.168.3.1（这个不要配置，去掉即可）

把节点 /etc/resolv.conf 指向 Kubernetes CoreDNS 后，节点本身也可以直接使用 *.svc.cluster.local。 这是可以工作的，因为你已经确认 10.96.0.2 在节点上可达。只是生产环境中通常更推荐让 Pod 使用 CoreDNS，而节点自己的 DNS 仍保留原来的企业/局域网 DNS；两者职责可以分开。

向外部暴露服务

截止到目前为位置，我们所有的服务都基于 k8s 内部，也就是说所有的服务都是在集群内部访问的，但是我们需要将我们的服务暴露给外部，以便我们集群外部访问我们的服务，其实原理是将外部的流量引入到 k8s集群的内部，使得 k8s集群可以路由这些请求，上个大章节的 springboot-test-service 就是这样将外部的请求导入的，使用的是 nodePort 类型的 service，比如说我们在外部的机器上执行请求

原理就是将流量导入到 pod 的存在的机器上, service 类型为nodePort，将实体 node 的30088 端口上监听的服务就可以处理这个请求了，并转发给对应的 service。这种方式有弊端，就是必须知道 pod 所在的机器，而 pod 所在的机器会随着k8s资源的调度进行变化。外部的机器如何通过一个媒介来访问到 k8s集群内部的服务呢？这就用到了 Ingress

什么是Ingress

Ingress 是 Kubernetes 中的一个资源对象，它用于将集群外部流量路由到集群内部的服务。关于 Ingress 的详细介绍可以参考：https://kubernetes.io/zh/docs/concepts/services-networking/ingress/

这里有几个修改我们需要注意

  1. 只调度到 master 节点
  1. ConfigMap 的配置项以及含义
键 含义 为什么这么配
forwardfor: “add” HAProxy 给上游追加 X-Forwarded-For 你的链路是 客户端 → Nginx → HAProxy → Pod。必须 append 才能让后端看到完整链路（客户端 IP 在 XFF 的第一个位置）。取值 add（追加）/update（覆盖）/ifmissing（没有才加）
use-forwarded-proto: “true” 信任上游传来的 X-Forwarded-Proto 你在 Nginx 上终止了 TLS，到 HAProxy 已经是明文 HTTP。不信任这个头，Spring Boot 生成的跳转链接会变成 http://，前端混合内容报警
max-connections: “10000” 全部 proxy 的总并发上限（Global） 默认 2000 对小集群够用；调到 1w 是给内部服务调用留余量。这是防御性上限，超了返回 503 而不是把节点打爆
timeout-client: “60s” 客户端侧超时（Global） 默认 50s。L7 场景下 60s 是比较通用的值；比上游 Nginx 的 proxy_read_timeout 略短会更早释放连接
timeout-server: “60s” 后端侧超时（Backend） Spring Boot 冷启动/慢接口常见，60s 避免 504；如果某个接口特别慢，可以在那个 Ingress 上用注解单独调大，不要全局放大
ssl-redirect: “false” 是否强制 80→443 跳转（Path） 关键：TLS 已经在外部 Nginx 终止，HAProxy 收到的是 HTTP。若这里为 true，HAProxy 会再回 302 到 https，而 Nginx 又转回来 → 无限跳转。所以必须关
  1. 启动参数
键 含义 为什么这么配
–configmap=ingress-controller/haproxy-ingress 指定全局 ConfigMap（格式 ns/name） v0.13+ 若这个 ConfigMap 不存在会直接 panic 退出，所以 ConfigMap 必须和它一起创建；注意"ns/name"两段都要对
–ingress-class=haproxy 只接管 kubernetes.io/ingress.class: haproxy 和 ingress-nginx 共存时互不干扰
–controller-class=haproxy-ingress.github.io/controller 只接管 spec.controller 等于这个值的 IngressClass 和 IngressClass 资源逐字对齐；同时它是区分"同集群多套 HAProxy Ingress"的手段
–election-id=class-haproxy.haproxy-ingress.github.io leader 选举的锁名 v0.15+ 的默认格式是 class-%s.haproxy-ingress.github.io（%s 填 class 名）。写全是为了显式，也避免有人改了 class 名却忘了改这个导致两套控制器抢同一把锁
–update-status=true 把节点 IP 回填到 Ingress 的 status.loadBalancer.ingress 默认就是 true，写出来是为了说明"它依赖 leases 权限 + leader 选举"，别把 RBAC 那几条删了
–report-node-internal-ip-address=true status 里用节点内网 IP 你的节点只有 InternalIP，没有 ExternalIP，不加这个 kubectl get ingress 的 ADDRESS 列会一直是空的（很多人以为控制器没工作）
–watch-gateway=false 不监听 Gateway API CRD 你没装 Gateway API CRD，v0.14+ 默认开启会不停报"找不到 CRD"的错日志，掩盖真正的错误。关掉后 RBAC 里 gateway 那两段也可以删
–reload-strategy=reusesocket 重载时把监听 socket 交给新进程（无损） v0.8 起就是默认值。写出来是因为它直接影响"改配置会不会断连接"，值得显式留痕
–v=2 日志级别 （1=info，2=+debug） 排障期用 2，稳定后可降到 1 减少日志量
  1. 端口与探针
  1. –update-status=true，控制器需要知道自己在哪个 namespace（用来给自己打选主/状态相关的东西），必须通过 Downward API 注入 POD_NAMESPACE。我上一版清单漏了这段 env。
