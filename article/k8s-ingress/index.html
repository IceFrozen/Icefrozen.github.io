一、为什么需要 Ingress

我们先从"没有 Ingress 的世界"说起。在 Kubernetes 里，Pod 的 IP 是不稳定的（重建就变），所以 Kubernetes 提供了 Service 作为一组 Pod 的稳定访问入口。但要把服务暴露到集群外部，Service 只有三种类型：

类型 工作方式 问题
ClusterIP 只分配集群内虚拟 IP 集群外访问不到
NodePort 在每个节点的 30000+ 端口上开洞 端口难管理、节点暴露面大、无七层能力、无 TLS 终止
LoadBalancer 每个 Service 申请一个云厂商四层 LB 一个 Service 一个 LB，成本高、公网 IP 爆炸，仍然只有四层能力

假设你有 50 个微服务，用 LoadBalancer 就意味着 50 个公网 IP + 50 个 LB，而且你依然无法做到：

  • 按域名（a.example.com / b.example.com）路由；
  • 按路径（/api → 服务 A，/web → 服务 B）路由；
  • 统一的 HTTPS 证书管理与 TLS 终止；
  • 灰度发布、限流、鉴权、重写等流量治理能力。

Ingress 要解决的核心问题就是：用一个（或少数几个）集群入口，把七层 HTTP/HTTPS 流量按需分发到集群内众多的 Service。 它是 Kubernetes 里的"反向代理声明规范"，等价于集群内的 Nginx/Envoy 网关。

一句话总结 Ingress 的目的：

统一入口（省成本与公网 IP） + 七层路由（host/path） + 集中式 TLS 与流量治理 + 声明式、可移植的配置。

二、整体架构

2.1 分层架构图

要点：外部 LB 只负责把流量"扔进"集群，真正的七层决策发生在 Ingress Controller 这个 Pod 里。

2.2 控制面与数据面分离

这是理解 Ingress 最关键的一点：

Ingress 资源本身不做任何转发。它只是一份"声明"（存在 etcd 里的 YAML）；真正干活的是 Ingress Controller。

所以如果你 kubectl apply 了 Ingress 却访问不通，第一件事是检查集群里到底有没有装 Ingress Controller —— 光有 Ingress 资源，K8s 默认什么都不会发生。

2.3 三个核心对象

IngressClass 的意义：一个集群里可以同时装多个 Controller（比如内网用 nginx、公网用 APISIX）。每个 Ingress 通过 spec.ingressClassName 明确归属，避免多个 Controller 抢同一条规则互相覆盖。

三、技术原理

3.1 Service（四层）与 Ingress（七层）的关系

Ingress 不是 Service 的替代品，而是 Service 上游的一层。 规则里的 backend 指向的仍然是 Service:Port，而不是直接写 Pod。这样 Pod 的漂移、扩缩容仍然由 Service/EndpointSlice 负责发现，Ingress 只负责"选哪个 Service"。

3.2 一次请求的完整链路

关于第 5 步补充一句：ingress-nginx 在 nginx 里用 balancer_by_lua + 共享内存动态维护 upstream 列表，因此 Pod 扩缩容不会触发 nginx reload，避免长连接抖动；只有路由规则本身变化才需要 reload。

3.3 路径匹配规则（pathType）

pathType 含义 示例
Prefix 前缀匹配，按 / 分段，不做字符串包含 /api 匹配 /api、/api/v1；不匹配 /apix
Exact 完全相等（大小写敏感） /foo 只匹配 /foo，不匹配 /foo/
ImplementationSpecific 交给 Controller 自己解释 nginx 下配合 use-regex 注解可写正则

注意 Prefix 的分段语义是很多人踩坑的地方：/foo 不会匹配 /foobar，但会匹配 /foo/bar。

3.4 TLS 终止示意

证书可以手工创建 Secret，也可以用 cert-manager 配合 Let’s Encrypt 自动签发与续期（生产推荐）：Ingress 上打 cert-manager.io/cluster-issuer 注解，cert-manager 自动申请证书并写入 Secret。

3.5 灰度发布（Canary）原理

ingress-nginx 的灰度实现：同一 host+path 下，如果存在带 canary: "true" 注解的 Ingress，Controller 会把它作为主 Ingress 的"影子"规则，按权重/Header/Cookie 分流。

六、Ingress 的定位与演进

Ingress 的最大遗留问题是：路由/流量治理能力（重写、灰度、限流）没有标准化，全靠各家 Controller 的 annotations，不可移植。这也是 Gateway API 出现的直接原因。Ingress 目前处于"冻结演进"状态（不会再有新功能），Kubernetes 官方主推 Gateway API。

实践建议：

  • 存量集群：继续使用 Ingress 完全没问题，它是稳定且广泛支持的 GA 特性；
  • 新集群或有复杂流量治理需求：直接上 Gateway API（Envoy Gateway / Nginx Gateway Fabric 等）；
  • 无论如何，先确认你的 Controller 是否在活跃维护。

七、小结

  1. Ingress = 声明，Controller = 实现。只 apply Ingress 资源而不装 Controller，什么都不会发生。
  2. Ingress 是七层网关，Service 是四层负载，两者是上下游关系：Ingress → Service → Pod，Controller 通常还会绕过 ClusterIP 直连 PodIP。
  3. 核心价值：一个入口承载多个服务（省 LB 与公网 IP）、host/path 七层路由、集中 TLS 终止、灰度/限流/鉴权等流量治理。
  4. 落地时先定三件事：用哪个 Controller、怎么把流量送进集群（LoadBalancer / hostNetwork / NodePort）、证书怎么签发与续期。
  5. 长期看，Gateway API 是官方演进方向，新项目值得优先评估。
